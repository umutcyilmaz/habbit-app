# 15-Day Product Reset

Phase 1U is the third executable new-product feature. It shares this directory with legacy Ten-Day Reset, whose screens, README, and `/reset/...` routes remain unchanged. New product Reset uses only:

- `/bloom/reset/baseline?journeyId=...`
- `/bloom/reset/progress?journeyId=...&attemptId=...`
- `/bloom/reset/completion?journeyId=...&attemptId=...`
- `/bloom/reset/assessment?journeyId=...&attemptId=...`

Each route delegates to `screens/ResetProductScreen.tsx`. `useResetFeature.ts` connects canonical provider reads, display time, navigation, and the existing flow API. `resetController.ts` coordinates commands and receipts; `resetView.ts` validates route presentation and uses existing Reset selectors. There are no direct persistence calls, pure transition calls, new provider accessors, or mutation IDs/timestamps generated by these modules.

Baseline collects the three existing `ResetBaseline.selfReport` fields without medical interpretation. It omits optional historical aggregates: no canonical aggregate helper currently derives them. Explicit submission calls `startFromBaseline({ selfReport })`; the flow creates the baseline and attempt facts. Only a durable receipt triggers replacement with the canonical active attempt's progress route.

Progress comes from `getResetProgress(reset, displayTime)` and `getResetRestrictionStatus(reset, displayTime)`. The exact boundary is 15 elapsed 24-hour periods after the **current attempt** start. A stale `active` status cannot extend behavioral restriction. The display combines current selector-derived completed days with the stored best for an effective best and never persists ticks. At the boundary, an explicit Continue opens completion; a second explicit action invokes `completeElapsed()`. The transition records the actual period end from the attempt start, independent of when it is observed. Durable completion opens assessment.

Manual violations support `masturbation`, `intentionalExplicitContent`, and `masturbationWithExplicitContent`. A confirmation explains the restart and is consumed before one `recordViolation({ reason, source: { kind: "manual" } })` call. The flow creates all mechanical identities/times. The transition archives the prior attempt and starts its replacement; intentional-content effects on active Content-Free are part of the same atomic Reset command. The feature never issues a separate Content-Free write.

History preserves violation IDs, attempt IDs, reasons, sources, occurrence/recording times, recorded status, and undone tombstones. Only the latest recorded Reset entry is offered as a candidate for `undoViolation({ violationId })`, regardless of manual/session source. This does not promise reversibility: the transition owns archived-attempt linkage, Content-Free linkage, source ownership, best restoration, and tombstones. A rejected undo shows neutral unavailable feedback. Successful undo restores the prior canonical attempt and linked Content-Free state atomically.

Assessment collects the five exact canonical answer fields, with all choices initially unanswered. The controller takes `resetJourneyId`, `resetAttemptId`, and `baselineId` from the validated current assessment-pending Reset. Readiness is descriptive; `notReady` and `notSure` do not block completion. The transition owns Tracking enablement. Durable assessment completion returns to the existing Today route, without creating a recommendation.

All commands recheck the exact scalar route IDs and displayed immutable Reset snapshot against `getAcceptedState()` immediately before dispatch. Undo also checks the exact current candidate. Stale, missing, repeated, mismatched, completed-state, or unmounted handlers cannot target another attempt. The controller captures the exact accepted successor before awaiting persistence: after restart/undo, the old URL is not mistaken for the successor identity. Save/retry feedback remains visible until acknowledgement. Only the exact current durable successor may navigate to its new/restored progress route, assessment, or Today.

Every dispatched mutation preserves `Promise<BloomPersistedMutationResult>`. Duplicate presses share an in-flight operation, and failures retain the original accepted state and retry token. `retryPersistedMutation(retryToken)` retries persistence only, without replaying commands or regenerating IDs/timestamps. Navigation is guarded while saving; receipt callbacks and explicit continuation recheck current identity. Mount, render, refocus, and display ticks never trigger a write or automatic lifecycle redirect.

`scripts/verify-bloom-reset-feature.ts` runs through `npm run verify:persistence`, alongside route and existing product verification. Persistence remains version 7 at `bloom.localState.v7`, with no schema/migration change. Home/Today remain unwired. Reset recommendation, starting recommendation, and Urge Control remain deferred; the four earlier Masturbation/Content-Free routes remain ready with unchanged behavior.
